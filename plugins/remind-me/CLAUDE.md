# CLAUDE.md

This covers the `remind-me` plugin. The registry-level rules are in the repository root's `CLAUDE.md`.

## What it is

One skill and two scripts. `scripts/collect.py` turns a day of transcripts into a digest and looks up what is true now; `scripts/render.py` turns the model's judgement and that digest into an HTML page and the summary the session prints. The model reads only the digest and writes only the judgement: topics, what was decided, done and found, what is open, and an emoji per repository. It came out of a manual reconstruction of one working day, which settled its shape.

## Decisions that are easy to undo by accident

- **Live state is required, not an option.** The manual reconstruction listed six pull requests as awaiting review that had been completed the same day. A transcript records what was pending when a session stopped, so every pull request the collector recognises is looked up; the forms it recognises are the `AZURE_PR` and `GITHUB_PR` patterns in `collect.py`. A state that cannot be read, or a pull request named in a form it does not recognise, is reported as not checked, never as pending.
- **Figures come from scripts, judgement from the model.** The page's figures (the counts, the times on the timeline, token usage, the new pull requests and how many completed, the uncommitted and unpushed counts), the folders, and the commands that reopen a session are copied from the digest by the renderer, never written by the model. What the model writes is the headline, the topics, each line of what happened and what is open, and each repository's emoji. The emoji is neither a figure nor a judgement of the day, only a mark to find a repository by, so a mark that cannot be used falls back to the initial without failing the run. Item text can still quote a number a session wrote, such as a ticket key or a count from a reply, and nothing checks it; the renderer shows no pull request's state of its own, so a merged or abandoned pull request reaches the page only through that text.
- **Resuming from the page is a link, not a command.** A `claude-cli://open` link with the session folder as `cwd` and `/resume <id>` as the prompt opens a new terminal in that folder with the command filled in, behind Claude Code's own "Prompt from an external link" warning, and Enter resumes the session there (checked by hand on Windows, 2026-10-06). The copyable command stays for when the link handler is not registered.
- **Cache reads are shown apart, not dropped.** They are the conversation history re-read on every request, so they measure how long and how large the sessions grew. They are cheap per token (0.05 times the base input price on Opus 5.5) but not free: on the day of the manual trial, 213M of them came to about 10.7M tokens at the base input price, more than the 4.3M written to the cache even with every write counted at the one-hour price of twice the base (8.6M).
- **No session title.** Claude Code's generated title names a session after its first prompt, and sessions drift: the one that started the manual trial was titled after listing last Friday's sessions and spent the day on mods and READMEs. The collector does not carry the title, and the model lists topics.
- **The day defaults to the last day with work, not to yesterday.** A Monday run reports Friday, and no calendar is needed to know that; what counts as work is below.
- **The current session counts.** A session resumed today in the repository where yesterday's work happened holds that work, so excluding the current session would drop it. Only the request that runs this skill is left out.
- **Resume always from the session's folder.** `claude --resume <id>` finds a session from any folder, but Claude Code is folder-scoped and a resume from elsewhere runs the session in the wrong one. The session's folder is the one it started in, where Claude Code keeps it; the `cwd` in later transcript entries follows the shell wherever a command moved it, and one session moved 48 times in a day (2026-10-06). Every resume command changes to the folder first, and the repository's panel also offers a plain terminal there, for when opening Claude Code is not allowed.
- **Azure DevOps ids are looked up across the collection, GitHub only from a full URL.** Azure numbers pull requests across a whole collection, so a bare `!151943` is enough with the organisation of any Azure repository in the digest. A GitHub number means nothing without its repository. A session in a GitHub repository can name Azure pull requests, and looking them up through `gh` returned nothing for all nine in the first run.
- **Lookups run in parallel.** One session that labelled old pull requests named 43 of them, and looking them up one at a time took 75 seconds against 14 in parallel.
- **No tables in the session summary.** The terminal prints a `<br>` inside a table cell literally, so the summary is headings and bullets.
- **A session is one bar, from its first entry to its last.** Drawing each stretch of activity as its own block read as several sessions, and once the bar was whole the stretches answered nothing the report asks, so the collector no longer computes them. Two sessions that ran at the same time in one repository get a row each.
- **Each button has one home.** A repository's header holds the folder's own ways in (a new session, the terminal command, the path) and one shortcut, resuming its most recent stopped session, so the usual way back needs no second click; a session's header holds only its own way back (resume, and the command to copy). The person kept the shortcut on 2026-10-08.
- **A repository git could not read is marked.** Without a mark it shows no chips, exactly like a clean one.
- **A running session cannot be resumed from the page, the current one included.** Resuming it would open the same session twice. A new session in the same folder is safe, because each session has its own id: two ran side by side in one repository on the day of the manual trial. The repository the report was asked from is marked rather than disabled.
- **Retention is not read.** The page never needed the value: the default day is one that has sessions, so its transcripts exist. Only an empty run needs it, and there the skill names `cleanupPeriodDays` and its default when no day was found or the day lies more than a week back, rather than on every empty day, most of which simply had no work. Reading the value properly meant five sources in Claude Code's own precedence, one of them an undocumented cache file, for that one sentence.
- **The default day is a day with work.** A day holding only `claude -p` runs, or only a run of this skill, would be picked and then report nothing, while the day before had work; the default counts only days with a typed prompt in an interactive session.
- **The day is a snapshot; the world is read as of now.** What the person did in the sessions, decided, done, found and left open, is judged from that day's prompts alone, so a report stays as the day was and a conclusion reached later is recorded on the day it was reached. **Reversed on 2026-10-08**: the report had judged open items as of now through `later_prompts`, which wrote a later day's decisions into this day's lists, prefixed with their date. The state outside the sessions, pull requests, branches and uncommitted work, is still looked up as of now and shown on the day's items, because no day's sessions record it and it is what started the plugin.
- **New pull requests are the person's.** Created that day is not enough: a session names colleagues' pull requests too. The person is the accounts the CLIs are signed in as (`az account show`, `gh api user`) plus the repositories' git emails, compared without case; a git email alone fails on GitHub, where it is often a noreply address.
- **A merged branch is not unpushed work.** Nothing fetches, so a merged branch's commits reach no remote-tracking ref in a clone that has not fetched since; matched to a completed pull request through its source branch in the same repository, it is marked `merged_by` instead of being counted as unpushed. The repository is part of the match because one ticket's branch can carry the same name in two repositories, and a match across them would hide real unpushed work.
- **A compaction summary keeps its end.** Its last sections are what was still pending and the next step, which a cut at the start dropped; the digest keeps its first 1,000 and last 3,000 characters.
- **What happened mirrors what is open.** Decided, done and found answer decide, do and find out, one each, and an event goes in exactly one of them. The first page held only done, and the run of 2026-10-08 put a cause the session had established into it, which read as finished work. Every choice the person made is decided, carried out or not, and done says only what was produced: the run of 2026-10-08 split one event across both when carried-out choices had to go in done, and the choices are what explain the work, and what a planning-heavy day is picked up from. Work that only established a fact is found (both ruled 2026-10-08).
- **The report carries the work, not the data the work touched.** The digest holds transcript excerpts, and a session that queried production or handled customer records carries them into it; the report and its page outlive the digest on disk and can be shared. So the skill leaves out credentials, personal data, third-party identifiers and anything read from a production system, keeps work identifiers such as ticket keys, pull requests and branches, and reads the digest in place without copying it. A run on 2026-10-08 met a day whose digest held production account ids, record counts and colleagues' names, and two runs had copied the digest to a scratch file to read it.
- **The headline carries no counts.** It is the one line the model writes above the figures, and the first version said 51 pull requests where the day had opened 7.
- **`claude -p` runs are left out by `entrypoint`.** Their transcripts say `sdk-cli`. They are scripts and probes, not work a person left open.
